# Бейджи и скриншоты в README

## Как устроены бейджи

Небольшие плашки под названием проекта называются бейджами (badges). В этом репозитории они загружаются с [Shields.io](https://shields.io/). В README используется обычный Markdown: картинка внутри ссылки.

```markdown
[![Описание картинки](URL_картинки)](Куда_вести_по_клику)
```

Например, бейдж лицензии MIT со ссылкой на файл лицензии:

```markdown
[![License: MIT](https://img.shields.io/badge/License-MIT-blue)](LICENSE)
```

Для статического бейджа адрес имеет вид `https://img.shields.io/badge/Название-Значение-Цвет`. Цвет можно задать словом (`blue`, `orange`) или HEX-кодом без `#` (`FF5D43`). Пробел обозначается `%20`, буквальный дефис — `--`. Параметр `?style=flat-square` делает углы прямыми, а `?style=for-the-badge` увеличивает плашку. Дополнительные параметры соединяются через `&`. Подробнее — в [документации Shields.io](https://shields.io/badges/static-badge).

Текущие бейджи находятся в начале корневого [README.md](../README.md):

| Бейдж | Что показывает | Когда обновляется |
| --- | --- | --- |
| Release | Версию опубликованного GitHub Release, включая предварительные выпуски | Автоматически после публикации релиза; выбирается старшая версия по SemVer |
| License | MIT из файла `LICENSE` | Вручную при изменении лицензии |
| Stars | Число звёзд репозитория | Автоматически |
| Windows | Поддерживаемую платформу x64 | Вручную при изменении платформ |
| .NET | Версию платформы разработки | Вручную при обновлении .NET |
| Build & tests | Реальный результат workflow `build.yml` для push в ветку `master` | Автоматически после запуска GitHub Actions |

Автоматические бейджи могут обновляться с задержкой из-за кеширования. Release показывает опубликованный выпуск: его номер может отличаться от версии в исходниках и на скриншотах. Если репозиторий переименован или перенесён, замените `drkreis/ac-server-manager` в URL; при смене основной ветки обновите `branch=master` и фильтр ссылки на Actions. Статус сборки берётся из [существующего workflow](../.github/workflows/build.yml); писать вручную `build-passing` не требуется.

## Как добавить скриншот

1. Откройте нужный экран программы и сделайте снимок окна, например через `Win + Shift + S`.
2. Сохраните PNG в `docs/screenshots/` с коротким именем латиницей: например, `wizard-ru.png`. Перед публикацией проверьте, что на снимке нет паролей, токенов или личных данных в путях и логах.
3. В корневом README добавьте описание и картинку:

   ```markdown
   **Создание сервера** — выбор параметров нового сервера.

   ![Мастер создания сервера](docs/screenshots/wizard-ru.png)
   ```

4. Если нужно заменить существующий снимок, сохраните новый PNG под тем же именем. Обновите подпись версии в разделе Screenshots, если она изменилась.
5. Откройте Markdown Preview в редакторе или вкладку Preview при редактировании файла на GitHub. Для публикации включите в один коммит README и сами PNG, затем отправьте коммит в GitHub.

Пути считаются от файла Markdown: для корневого README это `docs/screenshots/...`, а для Markdown внутри `docs/` — `screenshots/...`. GitHub сам уменьшает большие изображения по ширине страницы. Блок `<details>` в README позволяет свернуть дополнительные снимки; пустые строки вокруг Markdown внутри него нужно сохранять.

Готовые снимки локальных UI-проверок лежат в `artifacts/`. Эта папка исключена из Git, поэтому выбранные PNG нужно копировать в `docs/screenshots/`. Добавлять всю папку `artifacts/` не нужно.
